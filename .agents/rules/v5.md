# v5 — règles d'assistance au code

Tu es un assistant avec des capacités avancées de résolution de problèmes. Ce
fichier définit les comportements qui maximisent la productivité et la sécurité
sur les tâches **centrées sur le code** de workflow-rs.

## 0. Hypothèses communes

- **Tâches cibles** : code Rust, configuration TOML, scripts, documentation,
  débogage, exploitation du pipeline.
- **Langue** : suivre la langue de l'utilisateur. Le projet est documenté en
  français ; les identifiants, commandes et messages de commit restent en
  anglais.
- **Priorité des règles** : système > règles du workspace > ce fichier (v5) >
  préférences locales.
- **Politique de complétion** : ne pas s'arrêter au milieu. Si une contrainte
  bloque, indiquer clairement ce qui est fait et ce qui reste.
- **Conflits** : si les instructions sont ambiguës ou contradictoires, demander
  une clarification brève plutôt qu'interpréter.
- **Style de réponse** : conclusions et changements d'abord ; explications
  minimales ; pas de longs raisonnements sauf demande explicite.

## 1. Classification et profondeur de raisonnement

### 🟢 Tâches légères

Exemples : correction de quelques lignes, vérification de config, explication
d'une commande, petite documentation.

- Trouver la solution par le chemin le plus court.
- Ne pas produire de plan lourd.
- Lire uniquement les fichiers nécessaires, corriger, rapporter en 1–2 phrases.

### 🟡 Tâches standard

Exemples : changement sur plusieurs fichiers, ajout d'une sous-commande CLI,
adaptation d'un test, mise à jour d'une doc de lot.

- Présenter une analyse concise et une checklist de 3 à 7 sous-tâches.
- Lire les fichiers liés, modifier par petits incréments.
- Lancer `cargo fmt`, `cargo clippy` et les tests ciblés.
- Résumer les fichiers modifiés et les limites.

### 🔴 Tâches critiques

Exemples : changement de config de production, bascule 5003/5004, sync
`--apply`, rétention, STEP1/STEP7 destructifs, modification du verrou, des
secrets, du webhook ou des modèles.

- Analyser l'impact et les risques, présenter un plan, attendre l'approbation.
- Prévoir le rollback, la sécurité et l'impact production.
- Exécuter par étapes sûres, avec vérification après chaque étape.

## 2. Politique d'utilisation des outils

### 2.1 Fichiers

- **Lecture** : `read` pour un fichier, `grep`/`glob` pour localiser.
- **Édition** : `edit` pour un changement ciblé, `write` pour une réécriture
  complète.
- **Répertoires** : `ls`/`find` via `shell` ou `glob`.
- **Création** : `write` après avoir créé les parents si nécessaire.

### 2.2 Memory bank

- Lecture chirurgicale uniquement.
- Utiliser `fast_read_file` avec un chemin **absolu**
  `/home/kidpixel/workflow-rs/memory-bank/...`.
- Le serveur `fast-filesystem` est enraciné hors du dépôt : vérifier que le
  contenu renvoyé appartient bien à `workflow-rs`.
- Mise à jour en fin de tâche via `edit`/`write` ou `fast_write_file`.
- Ne pas charger la memory-bank pour une tâche triviale.

### 2.3 Recherche

- `grep` pour les motifs, `glob` pour les chemins.
- `shell` pour `cargo`, `git`, `rg`, `sqlite3`, `curl`, `ffprobe`.
- Éviter de charger un JSON de tracking complet : utiliser `jq`, les
  réducteurs streaming ou `json_query_*`.

### 2.4 Parallélisme

- Lire plusieurs fichiers indépendants en parallèle.
- Les modifications de fichiers doivent rester séquentielles pour éviter les
  conflits.
- Ne pas lancer deux étapes matérielles en parallèle.

### 2.5 Web et navigateur

- Rechercher les informations de version, les breaking changes et les bugs
  connus quand une dépendance externe est en jeu.
- Ne pas démarrer de serveur local sans instruction.
- Ne pas utiliser le navigateur pour contourner un test reproductible en CLI.

### 2.6 Analyse statique

- `cargo fmt --check`
- `cargo clippy --workspace --all-targets -- -D warnings`
- Corriger immédiatement les erreurs introduites.

### 2.7 Outils autorisés et complexité

- Outils principaux : `read`, `edit`, `write`, `grep`, `glob`, `shell`,
  `execute`, `sequentialthinking_tools`, `shrimp-task-manager`, `json-query`.
- **Verrou de complexité** : pour une fonctionnalité majeure ou un projet
  entier, proposer `enhance_complex` ou un plan explicite.
- **Édition standard** : utiliser `edit` pour les changements substantiels.
- **JSON massif** : ne pas charger le fichier entier ; utiliser `jq` ou
  `json_query_*`.

## 3. Flux standard

### 3.1 Tâches légères

1. Résumer la tâche en une ligne.
2. Vérifier 1–2 fichiers.
3. Corriger.
4. Vérification minimale.
5. Rapporter en 1–2 phrases.

### 3.2 Tâches standard

1. Organiser le but, les contraintes et l'impact en 2–3 phrases.
2. Checklist de 3 à 7 items.
3. Lire les fichiers liés et implémenter par passes.
4. `cargo fmt`, `cargo clippy`, tests ciblés.
5. Résumer les changements et les limites.

### 3.3 Tâches critiques

1. Plan avec but, impact, risques et rollback.
2. Approbation explicite.
3. Exécution par petites étapes vérifiées.
4. Vérification finale et trace dans `memory-bank/decisionLog.md` si la
   décision est durable.

## 4. Erreurs, types, sécurité et coût

- **Erreurs de compilation/lint** : les corriger immédiatement. Si la cause est
  complexe, revenir à un état sûr et documenter.
- **Pas de dégradation silencieuse** : ne pas remplacer une erreur par un
  `unwrap`, un `allow` ou une valeur par défaut qui masque le problème.
- **Sécurité, production, coût** : toute modification de secrets, de rétention,
  de webhook, de verrou, de sync ou de chemins de production est une tâche
  critique. Plan et approbation obligatoires.
- **Données réelles** : `runtime/` et `/mnt/cache` ne sont pas des bacs à
  sable.

## 5. Style de sortie

- Tâches légères : 1–2 phrases.
- Tâches standard et critiques : titres, bullets, fichiers concernés, impact,
  vérifications.
- Citer le chemin des fichiers modifiés.
- Limiter les blocs de code au strict nécessaire.
- Ne pas exposer de secrets ni de chemins de credentials.
- Si l'utilisateur impose un format ou une longueur, le respecter.

- Lire `AGENTS.md` et `.agents/rules/codingstandards.md` avant toute
  modification de code.
- Ne pas modifier `/home/kidpixel/workflow_mediapipe`.
- Ne pas écrire dans `/mnt/cache` depuis un test.
- Ne pas lancer les moniteurs Python et Rust simultanément.
- Ne pas lancer STEP2/3/4 matérielles des deux stacks en même temps.
- Utiliser `--release` pour les étapes lourdes et le serveur.
- Consigner les décisions durables dans `memory-bank/decisionLog.md` et les
  écarts de parité dans `parity/DRIFT.md`.
