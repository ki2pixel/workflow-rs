# Lot B2.1 — consolidation temporelle et cache de frames

> Statut : implémentation terminée, pilote `report_only` exécuté sur les 13
> projets disponibles. Aucune activation de production, aucune modification
> de `config/config.toml`, du runtime ou de `/mnt/cache`.

## 1. Objet

Le pilote B2 a montré deux limites :

- deux logos animés restaient à 7/12, dont un scindé en 7/12 + 3/12 par le
  clustering strict (IoU ≥ 0,50, centre ≤ 10 px) ;
- le détecteur repayait 12 décodages ffmpeg alors que le gate OCR A2 venait
  déjà d'extraire les mêmes 12 frames à la même résolution.

B2.1 conserve le modèle, les seuils de détection (0,30 / 0,65), le mode
`report_only` et l'absence de décision. Il ne modifie que l'association
temporelle et le chemin d'extraction des frames.

## 2. Fusion temporelle des logos animés

### 2.1 Algorithme

Pour chaque détection, `post/logo.rs` tente d'abord l'association stricte
historique. Si aucun cluster ne correspond, un second passage utilise une
tolérance d'habillage animé :

| Critère | Strict | Animé |
| --- | ---: | ---: |
| IoU avec la boîte représentative | ≥ 0,50 | ≥ 0,35 |
| Distance des centres | ≤ 10 px | ≤ 25 px |
| Ratio de largeur | — | 0,50–2,00 |
| Ratio de hauteur | — | 0,50–2,00 |

Le cluster conserve la boîte de meilleur score pour la sortie ; l'association
relâchée ne modifie donc ni le score ni la bbox publiée. Le garde-fou de
taille évite d'absorber une boîte de bannière large dans un petit logo.

Les seuils sont exposés dans chaque annotation :

```json
"clustering": {"iou": 0.35, "center_px": 25.0, "size_ratio": [0.5, 2.0]}
```

### 2.2 Validation hors ligne

Les 242 frames D-060 ont été réévaluées avec le clustering relâché, en
groupant les 12 frames de chaque clip :

| Jeu | Strict | B2.1 |
| --- | ---: | ---: |
| Clips négatifs avec cluster persistant | 0/5 | **0/5** |
| Groupes de références avec cluster persistant | 21/30 | **26/30** |
| Dont boîte `gt_logo` correcte | 20/21 | **25/26** |
| Groupes A2 avec cluster persistant | 3/5 | **3/5** |

Les cinq groupes de références récupérés (Les Marseillais, Le Reste du Monde,
Le Cross, Les Traîtres, C'est la famille) sont tous corrects. Le seul groupe
persistant non apparié reste *Capital*, dont le logo est trop petit (échec de
détection, pas de clustering). Aucun clip négatif ne devient persistant.

### 2.3 Tests unitaires

- `cluster_absorbs_a_twelve_pixel_shift` : un déplacement de 12 px reste un
  seul cluster.
- `cluster_splits_a_distant_logo` : deux logos à 300 px restent séparés.
- `cluster_rejects_a_giant_size_change` : une boîte 2,5× plus large, même
  centre et IoU 0,40, est refusée par le garde-fou de taille.
- `animated_logo_is_recovered_by_relaxed_association` : le cas synthétique
  reprenant les deux boîtes réelles de « Manifestations » (7 frames A puis
  3 frames B, centres à ~20 px, IoU 0,65) donne un cluster à 10/12 et
  `detected=true`. L'ordre réel des détections est différent : la première
  boîte B précède le cluster dominant et reste à ~30 px, donc le
  sous-cluster de 3/12 n'est pas absorbé en ligne (voir 4.2).

## 3. Cache de frames partagé avec l'OCR A2

### 3.1 Architecture

`vision/frame.rs` expose un `FrameCache` mono-projet :

- 12 cases indexées, initialisées à `Pending` ;
- au premier accès, la frame est décodée par `grab_frame` puis conservée en
  `Rc<BgrFrame>` ;
- une frame absente est mémorisée (`Missing`) pour ne pas relancer ffmpeg ;
- une erreur transitoire laisse la case `Pending`, ce qui permet au second
  consommateur de réessayer.

Le cache n'est créé que si `a2_logo_detector = true`. Le gate OCR A2 le
remplit lorsqu'il est actif ; le détecteur de logos relit ensuite les mêmes
12 frames. Sans détecteur, A2 garde son extraction directe : la production
par défaut est inchangée. Sans OCR, le détecteur remplit le cache lui-même et
le coût ffmpeg reste celui de B2.

### 3.2 Mesures

Frame 1920×1080 de 60 s, modèle CUDA, session comprise (test labo
`--release`, le 2026-11-09) :

| Étape | Durée |
| --- | ---: |
| Chargement de la session `ort` (CUDA, warmup) | 1 480 ms |
| 12 frames, premier passage (ffmpeg) | 4 081 ms |
| 12 frames, second passage (cache) | **0,0 ms** |
| 12 inférences | 110 ms |

Un run antérieur du même test donnait 1 359 ms, 4 712 ms et 104 ms : la
variance porte sur le chargement CUDA et les décodages, pas sur le cache,
qui reste à 0,0 ms.

Le surcoût I/O du détecteur devient donc nul lorsque l'OCR A2 est actif ;
le coût résiduel est la création de session (≈1,4 s/projet) et l'inférence
(≈0,1 s/projet). La session reste détruite avant de relâcher le verrou
matériel : elle n'est pas conservée entre projets.

## 4. Pilote `report_only`

Même protocole et même corpus que B2 : 13 projets finalisés dont le brut est
byte-identique à l'assist, baseline et détecteur avec le même runtime OCR.

### 4.2 Fragmentation résiduelle de « Manifestations »

Le sous-cluster de 3/12 n'est pas absorbé en conditions réelles. L'ordre
des détections diffère du test unitaire : la première boîte du sous-cluster
apparaît au frame 1, à ~30 px du centre de la boîte dominante du frame 0,
au-delà de la tolérance de 25 px. Elle crée donc un second cluster ; les
détections suivantes de chaque groupe matchent ensuite strictement leur
propre cluster, et le passage relâché n'est jamais retenté. Le résultat est
9/12 + 3/12, persistence 0,75 : le logo est détecté, mais le sous-cluster
reste listé dans `top`.

Deux pistes sont identifiées, non implémentées dans B2.1 :

- fusionner les clusters après coup lorsque leurs boîtes représentatives
  satisfont le critère relâché et que leurs frames sont disjointes. La
  simulation sur les 242 frames D-060 donne 26/30 groupes de références
  (inchangé), 4/5 groupes A2 au lieu de 3/5 et 0/5 clip négatif ;
- utiliser un suivi avec prédiction de centre, qui absorberait le
  micro-mouvement sans élargir le seuil global.

### 4.3 Cache non sollicité par le pilote

Aucun des 13 projets ne déclenche le gate OCR A2 : aucun `post.json` ne
contient de bloc `ocr` et aucun candidat A2 n'est retenu. Le cache reste
donc vide, le détecteur décode lui-même les 12 frames et le coût observé
reste ~4,5 s/projet. La mutualisation est prouvée par le test labo (second
passage à 0,0 ms), mais elle ne réduit pas le coût sur ce corpus. Le gain
n'est acquis que sur les projets où A2 extrait déjà les frames pour l'OCR.

## 5. Limites et décision

- Le cache consomme environ 75 Mo (71 Mio) de RAM pendant un projet lorsque
  le détecteur est actif ; il est libéré à la fin du projet.
- Le cache suppose que l'OCR et le détecteur partagent la même durée et la
  même résolution source ; c'est le cas dans `run.rs`, mais un appel direct à
  `decide_a2` sans cache garde l'extraction historique.
- **Le cache n'a pas été exercé par le pilote** : aucun des 13 projets ne
  déclenche le gate OCR A2, donc le coût reste ~4,5 s/projet. Le gain de
  0,0 ms est prouvé en laboratoire, pas observé sur ce corpus.
- La session CUDA n'est pas réutilisée entre projets : le verrou matériel
  impose de détruire la session avant de le relâcher.
- Si `a2_ocr = false`, le détecteur paie encore 12 décodages individuels.
  Une extraction groupée (`select` FFmpeg) a été mesurée à ~3,0 s pour 12
  frames, soit un gain insuffisant pour justifier un second chemin.
- Le clustering relâché reste une heuristique validée sur 13 projets et
  242 frames D-060 ; il ne remplace pas un suivi temporel avec prédiction.
  Il est dépendant de l'ordre : un sous-cluster intercalé dont la première
  boîte est à ~30 px du cluster dominant reste séparé (4.2).
- Aucune activation de production : `a2_logo_detector` reste `false` par
  défaut et ne participe pas à la décision A2.
